# 迁移运维指南

当前自动化验证范围是 SQLite。迁移器提供计划预览、破坏性操作确认、事务回滚、状态记录，以及同一进程内的 SQLite 文件级串行锁；它不负责创建数据备份，也不能协调多个 Node.js 进程或多台主机。

## 执行前检查

先生成只读计划：

```typescript
const migrator = new ModelTableMigrator(db);
const plan = await migrator.dryRun();

console.table(plan.operations);
console.log(plan.requiresBackup, plan.warnings);
```

`dryRun()` 不创建业务表或 `lli_model_record`，也不更新模型快照。操作包含模型、表、目标对象、是否破坏性及提示。已从模型注册表移除的旧模型会显示为 `orphanTable`，迁移器不会自动删掉对应表。

以下操作要求重点审核：

- `dropColumn` 会永久丢失列数据，属于破坏性操作。
- 字段 `type`、`length`、`required` 变化可能重建列、截断数据或因现有空值失败，属于破坏性操作。
- 新增 unique 字段约束或索引可能因重复数据失败，计划会给出警告，但不会标记为数据删除。
- `orphanTable` 只提示人工处置，不会执行删表。

## SQLite 备份

`allowDestructive` 只表示调用方已经完成备份审核，不会自动复制数据库文件。建议流程：

1. 停止应用写入并等待进行中的事务结束。
2. 关闭所有指向该文件的 Knex 连接池。
3. 使用 SQLite 官方 backup API，或在确认没有活动连接后复制数据库文件及仍存在的 `-wal`、`-shm` 文件。
4. 在隔离目录打开备份，执行完整性检查，并至少验证关键表行数和一次恢复启动。
5. 重新启动连接，重新调用 `dryRun()`，确认计划未变化后再执行。

不要把 `lli_model_record` 的模型 JSON 快照当成数据备份；它只记录 ORM 模型定义，不能恢复业务数据。

## 执行与恢复

没有破坏性操作时：

```typescript
await migrator.syncAll();
```

存在破坏性操作时，未显式确认会抛出 `code: 'LLI400'`，完整计划位于 `error.detail.migrationPlan`。确认备份可恢复后执行：

```typescript
await migrator.syncAll({ allowDestructive: true });
```

SQLite DDL 与模型快照在同一事务内执行。失败时旧 schema 和旧快照会保留，并尽力把状态记录为 `failed`。修复数据或模型问题后，先再次生成计划，再重试迁移。若数据库自身无法完整回滚某项 DDL，应停止写入，从已验证的备份恢复，而不是手工伪造模型快照。

## 并发边界

同一个 Node.js 进程内，迁移器会按 SQLite 文件的绝对路径排队；即使创建了多个 `Database` 实例，同一文件也只会有一个迁移在执行。`:memory:` 数据库按实例隔离。

该锁不跨进程、不跨容器、不跨主机。多副本部署必须在发布系统中保证只有一个迁移任务运行，其他实例应等待迁移成功后再接收流量。PostgreSQL 的 advisory lock、DDL 一致性与恢复流程尚未纳入当前测试范围，不能根据 SQLite 结果推断其生产安全性。
