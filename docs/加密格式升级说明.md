# 加密格式升级说明

本文说明 `0.1.0` 加密格式升级后的兼容边界和已有数据迁移方法。迁移前必须备份数据库，并先在备份副本上验证 key、旧 IV 和旧摘要 salt。

## 格式变化

| 用途 | 旧格式 | 新格式 | 新写入行为 |
|---|---|---|---|
| 可逆字段 | `$EN$<CBC hex>` | `$EN$v2$<nonce>$<authTag>$<ciphertext>` | AES-256-GCM，每次生成随机 12 字节 nonce，并保存 16 字节认证标签 |
| 密码摘要 | `$EN$<SHA-256 hex>` | `$SC$1$<N>$<r>$<p>$<salt>$<derivedKey>` | scrypt，每次生成随机 16 字节 salt，参数写入摘要 |

旧 CBC 和 SHA-256 格式在 `0.1.x` 中保持兼容读取，计划最早在 `0.2.0` 移除。完成迁移前不要删除旧 IV 或旧摘要 salt。

## 可逆字段迁移

模型可以先把 `expansionConfig.type` 改为 `aes-256-gcm`。读取逻辑会同时识别新旧密文，但旧数据仍需要 `encrypt.iv`。

迁移必须读取数据库原始密文，不能使用已经由 ORM 解密的返回值。下面示例应按主键分批执行，并记录失败 ID：

```typescript
await db.transaction(async ({ trx }) => {
  const rows = await trx('secure_records')
    .select(['id', 'secret'])
    .whereLike('secret', '$EN$%');

  for (const row of rows) {
    if (!db.encrypt.needsEncryptionUpgrade(row.secret)) continue;

    const upgraded = db.encrypt.upgradeEncryption(row.secret);
    await trx('secure_records').where({ id: row.id }).update({ secret: upgraded });
  }
});
```

迁移完成后检查该列不存在 `$EN$` 开头但不以 `$EN$v2$` 开头的记录。确认备份可恢复、新密文可读取后，才能移除 `encrypt.iv`。

## 密码摘要迁移

密码摘要不可解密，因此不能离线转换。应在用户下一次成功认证时升级：

```typescript
const valid = db.encrypt.verifyHash(password, user.password, process.env.DB_LEGACY_HASH_SALT);
if (!valid) throw new Error('账号或密码错误');

if (db.encrypt.needsHashUpgrade(user.password)) {
  await db.query('user').update({
    where: { id: user.id },
    data: { password: db.encrypt.hash(password) },
  });
}
```

新 scrypt 摘要已经包含独立随机 salt，不读取全局 `encrypt.salt`。迁移窗口结束后，统计仍使用 `$EN$` 旧摘要的账号，并通过密码重置流程处理长期未登录用户。

## 失败与回滚

- GCM 认证失败会抛出 `LliDbError`，必须停止迁移并保留原值，不能写入空字符串。
- CBC 解密失败通常表示旧 key、IV 或密文错误，应记录记录 ID，不要记录密文本身。
- 回滚应用版本前，应确认旧版本不会尝试读取 `$EN$v2$` 或 `$SC$1$`；旧版本不认识新格式，因此数据库迁移不能与应用回滚分开设计。
- 推荐先灰度发布兼容新旧格式的代码，再分批迁移数据，最后移除旧配置。
